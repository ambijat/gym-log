# DS5 Workout Log — Project Audit

Read-only audit of the `gym-log` repository as of 2026-07-22 (HEAD `8a3cbfa`, v1.8 / versionCode 10).

## 1. What this project is

This is **not** a conventional native Android app. It is a [Bubblewrap](https://github.com/GoogleChromeLabs/bubblewrap)-generated **Trusted Web Activity (TWA)** — a thin native shell that opens a hosted Progressive Web App (PWA) in a Chrome Custom Tab that renders full-screen and looks native. Two things live in the same repo:

- **Native shell** (`app/`): Java/Gradle project that produces the installable `.aab`/`.apk`.
- **The actual product** (`index.html`, `sw.js`, `manifest.json`, `icons/`, `screenshots/`): a single-page PWA hosted at `https://ambijat.github.io/gym-log/` (GitHub Pages). The native app has essentially no logic of its own — all UI and behavior come from this web app.

```
gym-log/
├── app/                        Android TWA shell (Java, generated by Bubblewrap)
│   ├── build.gradle               twaManifest config + resValue generation
│   └── src/main/
│       ├── AndroidManifest.xml    Templated manifest (Bubblewrap markers)
│       ├── java/.../Application.java, LauncherActivity.java, DelegationService.java
│       └── res/                   Icons, splash, shortcuts, strings, colors
├── index.html, sw.js, manifest.json   The PWA itself (hosted separately on GH Pages)
├── icons/, screenshots/, graphics/     PWA/store art assets
├── privacy-policy.html                Hosted privacy policy
├── twa-manifest.json                  Bubblewrap's source-of-truth config (generates app/build.gradle values)
├── .well-known/assetlinks.json        Digital Asset Links (verifies TWA ↔ domain trust)
├── certificates/internal_cert.der     Android debug certificate (not the release key)
├── docs/RELEASE_PROTOCOL.md           Manual release runbook
└── android.keystore, local.properties Local-only, git-ignored signing/SDK config
```

## 2. Native shell (`app/`)

- **Package / identity**: `com.ambijat.gymlog`, app name "DS5 Workout Log", launcher label "DS5 Log".
- **SDK levels**: `minSdkVersion 21` (Android 5.0, 2014), `targetSdkVersion 35`, `compileSdkVersion 36`.
- **Toolchain**: AGP `8.9.1`, Gradle wrapper `8.11.1`, Java 8 source/target compatibility.
- **Single dependency**: `com.google.androidbrowserhelper:androidbrowserhelper:2.6.2` (the Bubblewrap/TWA support library). No other runtime dependencies.
- **Three Java classes**, all thin subclasses of androidbrowserhelper with empty bodies:
  - [Application.java](../app/src/main/java/com/ambijat/gymlog/Application.java) — no-op `onCreate`.
  - [LauncherActivity.java](../app/src/main/java/com/ambijat/gymlog/LauncherActivity.java) — sets portrait orientation on API 27+ only (a documented workaround for a transparent-background crash on Oreo and below).
  - [DelegationService.java](../app/src/main/java/com/ambijat/gymlog/DelegationService.java) — no-op, wires up notification delegation from the web app to the TWA.
- **Manifest capabilities** ([AndroidManifest.xml](../app/src/main/AndroidManifest.xml)):
  - One runtime permission: `POST_NOTIFICATIONS`.
  - `autoVerify` intent-filter on `https://ambijat.github.io/gym-log/*` (App Links / Digital Asset Links).
  - `SEND` intent-filter for `text/plain` → feeds the PWA's Web Share Target (`?share=1`).
  - A `FileHandlingActivity0` activity-alias registered for `content://` URIs with `application/json` and `text/csv` MIME types → feeds the PWA's file-import feature.
  - A launcher shortcut ("Log a workout") and a `FileProvider` scoped to a `twa_splash/` files-path (splash-screen image only).
  - `TrustedWebActivityService` (`DelegationService`) exposed for notification delegation, gated by `enableNotification` (currently `true`).
- **Build-time codegen**: `app/build.gradle` defines `twaManifest` inline and a `generateShorcutsFile` task (note the typo in the task name — cosmetic, harmless) that regenerates `res/xml/shortcuts.xml` from it on every `preBuild`. This duplicates `twa-manifest.json` at the repo root — the two must be kept in sync by hand (Bubblewrap normally regenerates both from one edit via its CLI).

## 3. The PWA (the real app)

[index.html](../index.html) is a single ~500-line self-contained file (inline `<style>` and `<script>`, no build step, no framework, no bundler) implementing:

- **6 fixed muscle-group categories** (Chest+Tri, Back+Bi, Shoulders, Legs, Core+Abs, Cardio), each with a hardcoded list of exercises — there is no way to add custom exercises from the UI.
- **One-tap logging**: tapping an exercise stamps `{id, ex, group, ts}` (ISO timestamp) into an array kept in `localStorage` under the key `ds5log:entries`. There's an in-memory fallback (`memFallback`) if `localStorage` is unavailable.
- **"Completed today" stars**: exercises tapped today get a star badge, recomputed from the log rather than separate state (added in commit `191336f`).
- **History view** with filters (all / today / 7d / 30d), grouped by local calendar day, with per-entry delete (confirm-gated).
- **Import**: accepts JSON or CSV (hand-rolled quoted-field CSV parser), de-duplicates against existing entries by `ts|ex|group`, wired to both the OS file-handler (`launchQueue`) and Web Share Target.
- **Export**: CSV or JSON, via clipboard copy, file download, or `navigator.share`/`mailto:` fallback.
- All user-facing text interpolated into `innerHTML` is passed through an `esc()` HTML-escaper — no obvious injection surface from log data.
- No analytics, no network calls, no external API — the only outbound network activity is the Google Fonts stylesheet link and whatever GitHub Pages/service worker needs to fetch the shell.

[sw.js](../sw.js) — versioned cache (`ds5-workout-v10`, bumped by hand alongside app releases), network-first for navigations, stale-while-revalidate for other GET requests, old caches purged on activate.

**Data model caveat worth knowing**: everything lives in browser `localStorage` on-device. There is no server sync — uninstalling the app, clearing site data, or switching devices loses the log unless the user has manually exported it. `privacy-policy.html` documents this accurately.

## 4. Signing, trust, and secrets hygiene

- `android.keystore` and `local.properties` exist on disk but are **correctly excluded** via `.gitignore` (`*.keystore`, `local.properties`) and are **not** present in git history (verified via `git log --all -- android.keystore`).
- `certificates/internal_cert.der` **is** committed, but it's the auto-generated Android **debug** certificate (`CN=Android Debug`, self-signed, validity 2026–2056) — not the release signing key. Committing this is low-risk (debug certs are not treated as secret by convention), but it's unusual to check in at all; worth confirming it's not accidentally referenced by any signing config.
- `.well-known/assetlinks.json` declares the *release* certificate's SHA-256 fingerprint (`A3:02:6F:...`), which does **not** match the committed debug cert — consistent with the debug cert being an unrelated, non-sensitive artifact.
- [docs/RELEASE_PROTOCOL.md](../docs/RELEASE_PROTOCOL.md) is a well-written manual runbook (SDK/JDK paths, build, sign, verify, commit, Play Console upload, smoke-test checklist) and explicitly warns not to commit passwords, `local.properties`, keystores, or build artifacts. It embeds machine-specific absolute paths (`/media/ambijat/...`, `/home/ambijat/...`), so it's tied to this one developer's machine rather than being portable/CI-ready.
- There is no CI/CD (no `.github/workflows`, no other pipeline config) — releases are entirely manual per the runbook above.

## 5. Dependency & tooling notes

- `build.gradle` declares `jcenter()` as a repository in both `buildscript` and `allprojects` blocks. **JCenter was sunset in 2021/2022** and no longer accepts new packages; existing cached artifacts may still resolve for now, but this is a deprecated repository that could break resolution unexpectedly and should eventually be dropped in favor of `mavenCentral()` (the single dependency, `androidbrowserhelper`, is available there).
- Only one third-party dependency in the whole native project (`androidbrowserhelper:2.6.2`) — minimal attack surface / maintenance burden by design (typical for Bubblewrap TWAs).
- `minifyEnabled true` for release builds; `lintOptions { checkReleaseBuilds false }` disables lint gating on release builds specifically.
- No README or LICENSE file at the repo root.

## 6. Housekeeping observations

- Task name typo: `generateShorcutsFile` in [app/build.gradle](../app/build.gradle) (should be `generateShortcutsFile`) — cosmetic only, task name isn't referenced elsewhere.
- `manifest-checksum.txt` at the repo root holds a single hash (Bubblewrap's drift-detection marker for `twa-manifest.json`); it's a generated file but is tracked in git, consistent with Bubblewrap's own conventions.
- `twa-manifest.json` and `app/build.gradle`'s inline `twaManifest` map are two independent sources of truth for the same config (name, colors, shortcuts, version) — the release runbook already calls out keeping `versionCode`/`versionName` in sync between them; the same applies to any other field either file might drift on.
- `.vscode/` is gitignored and not tracked — clean.

## 7. Summary

A well-scoped, minimal-surface-area TWA wrapper: almost no native code, one dependency, no telemetry, on-device-only data, and an accurate privacy policy. The two things worth a deliberate decision (not urgent, nothing broken today) are the deprecated `jcenter()` repositories and the fact that the entire release process is manual and machine-specific with no CI safety net.
